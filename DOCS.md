# Protect AnyChime documentation

## Chimes and speakers

Configure the app's verified Protect console connection in the web interface. Configure the local Protect management username/password in Home Assistant's app Configuration tab. Console certificates and accounts are installation-specific; credentials never belong in the source tree. The existing adoption, automatic-adoption option, native chime protocol, management ownership checks and ringtone upload/storage remain in use.

Available speakers are individual eligible `media_player` entities. HA group entities remain individual choices; AnyChime does not inspect `group_members` to decide chime membership. Discovery refreshes names, availability, platform and device metadata without changing fixed sets. Native UniFi devices, known incompatible routes and entities without PLAY_MEDIA capability are hidden. Missing previously selected entities remain visible as offline members.

A chime owns a stable key and an ordered member list in private `/data/chimes.json`. A first fresh chime may use the existing `primary` slot; additional chimes receive independent random keys. Member additions, detachments and moves update the registry atomically and never move or replace identity/ringtone directories. Removing the member currently used as a representative changes only the representative entity, not the chime key or its Protect pairing. Moving the final member is explicitly refused so no empty active chime or unconfirmed Protect deletion can result.

Use drag handles, +, per-chime Add speaker, member ×, or keyboard pickup/drop. Membership changes remain provisional in the UI until the server accepts them. Failed operations restore the previous display. Chime-menu Remove and last-member × require confirmation, then call the existing local-account, pinned-session, owned-device deletion flow. A failed deletion keeps the identity paused and available for retry; only confirmed removal allows identity/ringtone cleanup. Removing a virtual chime from Protect also disables it in AnyChime. Automatic background deletion of historical unconfirmed identities is not performed.

The ingress-only membership endpoint is `POST /api/chimes/members`, with an explicit `confirmed: true`, `action` (`add`, `move` or `remove`), selected `entity_id`, and a destination `target_key` or source `key`. A null destination creates a chime. Last-member removal additionally requires `confirm_last: true`. A removal cannot be hidden inside an ordinary member move. Product image selection and console connection endpoints remain separate.

Upgrade migration is idempotent. Existing entries retain their keys, identity directories, ordered members, adoption and ringtone files. `/data/chime-schema.json` records completion. Unfinished legacy grouping transitions, conflicting old membership, or historical unconfirmed saved identities are held for review. The app does not replay old deletion instructions or mutate those identities. The user removes the affected chimes using the confirmed flow; `POST /api/chimes/migration/finish` explicitly finishes review once no held identity remains. An outstanding ordinary removal flag is retained unchanged and can be retried using Remove.

After completed migration, obsolete grouping preferences, microphone profiles, the synthetic click cache and the rendered latency cache are removed. Export omits them. Import validates older archive checksums before ignoring obsolete files; any unfinished transition is converted into explicit review state instead of disappearing. Normal HA app backups include all remaining `/data` state. The explicit export/import mechanism retains identities, current sets, trust, ringtones, manual offsets and migration review state.

The app uses host networking, an ingress/media listener on 48200 and per-virtual-device management forwarding. Network permissions are NET_ADMIN and NET_RAW. Dedicated nftables rules and journals are owned and cleaned up by the app; other applications' rules are not targets. HA OS has been exercised live; Supervised/Debian and different Docker/network backends require their own validation. No source release includes runtime identity, account, certificate or audio material.

## Timing

Timing is available for a chime with at least two configured members. Each member has a 0–500 ms slider and Save. Test requests playback only after an explicit click, at 10% by default. All normal Protect test ownership/adoption checks remain in effect. Editing or saving does not play sound. Saved offsets apply to doorbell rings as well as tests.

Manual values are private in `/data/latency-delays.json`, keyed by HA device ID, falling back to `entity_id` for players without a device. Existing values survive upgrade and export/import. Offline members retain their saved values. Two entities for the same HA device share its stored offset. A single effective playback target ignores offsets, even if more than one configured member collapses onto that target.

The backend preflights all selected members, filters off/standby/unavailable/unknown/muted players and computes effective output requests. A zero Protect volume performs no HA playback. Announcements retain `announce: true` and requested `extra.volume`; that extra volume is integration-specific. Normal playback checks or sets volume before sending media. Existing consistent music groups deduplicate to their reported coordinator. Sonos AudioClip requests remain per speaker. Normal Sonos group playback deduplicates as a group; incompatible mixed announcement capability in one Sonos music group fails before audio.

Effective requests run concurrently. Every repetition registers a fresh batch. For two or more requests, the URL query contains `ac_sync=<batch>.<member>` with random opaque identifiers. Offsets are stored in the server batch and never accepted from URL parameters. The expected count is per output token, so a shared proxy IP does not collapse distinct members. Unknown, expired, duplicate, missing or wrong-path tokens do not wait or add arrivals.

Only the first non-probe GET starting at byte zero waits, before headers. HEAD, tiny probes and later ranges bypass the barrier. One common release epoch is set when all members arrive or the one-second deadline expires. An output waits until that epoch plus its saved offset, with no more than 1.5 seconds of requested waiting in total. Late wakeups do not accumulate a new full offset. Batches expire and their count is bounded; capacity exhaustion retains plain original media delivery without a new barrier. Failed HA calls release pending waiters without retrying audio.

No ringtone is rendered or transcoded by AnyChime. The original stored MP3 is served with its usual range support. Repetitions remain separate requests after original duration + 50 ms; there is no combined-repeat file or alternative playback mode. A compact status summary reports expected/distinct downloads, arrival spread and release reason, with no IPs, tokens or URLs.

Download timing does not prove audible alignment. Players may buffer differently, proxy or cache requests, or perform transcoding. Grouped outputs cannot be individually delayed behind a single HA group/coordinator request. When that group participates with another output, its coordinator's saved delay is used if selected, otherwise the first selected member's. Previously calibrated numbers can be retained while producing different audible results from the old file-silence method. Real listening verification is required; no automated test here plays on real speakers.
